# 🧠 BRAINPOOL OS — 전체 상태 분석 보고서 (2026-05-08)

> **목적**: 현재 프로젝트의 모든 문제점, 설계 의도, 실제 구현, 데이터베이스 스키마, 모듈화 상태를 한눈에 파악하여 어떤 AI나 개발자도 즉시 상황을 이해하고 복구/재구성할 수 있도록 함.

## 1. 프로젝트 개요

### 1.1 원래 목표 (설계 의도)
- 한국어-베트남어 **실시간 번역 채팅 플랫폼**
- 로그인 없이 `device_id` 기반 동작
- 번역 결과를 **DB 캐싱**하여 AI 호출 최소화
- **모듈화된 아키텍처**: 각 Core(CoreRing, CoreChat, CoreNull, CoreChild)를 독립적인 **npm 패키지**로 발행 → 조립하여 사용
- 계층: **모듈(순수함수) → 엔진(조합기) → 레이어(서비스)**
- 모든 함수 `(ctx) => ctx` 규격, `throw` 금지, `_error` 필드 사용
- CSS 토큰 시스템 (`var(--*)`만 사용, px/hex 직접 금지)

### 1.2 현재 상태 요약
- **배포 URL**: https://brainpool-clean.vercel.app
- **동작 상태**: 
  - CoreRing API: ✅ (로컬/배포 모두 번역 가능, 단 호출 URL 문제 일부)
  - CoreChat API: 🔴 (메시지 저장 실패 - DB 컬럼 부족)
  - CoreNull API: 🔴 (DB 컬럼명 불일치, 액션명 불일치)
- **빌드**: TypeScript 에러 해결 후 성공
- **모듈화**: 심각한 경계 붕괴 및 중복 코드 존재
- **패키지 발행**: 전혀 준비 안 됨 (모노레포 없음)

## 3. 심각한 문제점 상세

### 3.1 DB 스키마 불일치 (가장 치명적)

#### 3.1.1 `chat_messages` 테이블 (실제)
```sql
id, room_id, user_id, message, created_at, updated_at
```
**문제**: `translated`, `target_lang`, `translation_error`, `original` 컬럼 없음.  
→ `/api/chat/send`에서 DB insert 실패 (500 오류)

#### 3.1.2 `tp_translations` 테이블 (실제)
```sql
standard_word, southern_word, hue_word, mekong_word, meaning_ko, meaning_en, 
example_northern, example_southern, notes, part_of_speech, ... (다수 컬럼)
```
**문제**: 
- 코드에서 `example_hue`, `example_mekong`, `cultural_note` 등을 참조 → 존재하지 않음
- 검색 조건이 `standard_word`로 되어 있으나, 의미상 `meaning_ko`로 검색해야 함

#### 3.1.3 `tp_conflicts`, `tb_trans_logs` 테이블
- 일부는 구조 확인 안 됨. 코드에서 사용 중이지만 실제 존재 여부 불명확.

### 3.2 레이어/모듈 경계 붕괴

| 문제 | 구체적 예시 |
|------|-------------|
| **중복 레이어** | `CoreChatLayer.js`가 brain-engine/layers/ 와 루트 디렉토리에 각각 존재 (내용 다름) |
| **자기 자신 HTTP 호출** | `CoreChatLayer.js`에서 `fetch('/api/brainpool')` 호출 → 순환 의존성 |
| **번역 로직 3중 중복** | `translate.js`, `TranslationLayer.js`, `CoreRingLayer.js` 모두 DeepL 호출 코드 보유 |
| **직접 인스턴스화** | `CoreRingLayer.js`가 `new LanguageLayer()`, `new TranslationLayer()`로 생성 → 엔진/레이어 경계 모호 |
| **파이프라인 무시** | `runPipeline`이 있지만 실제로는 직접 `.process()` 체이닝 |

### 3.3 API 라우트 문제

#### 3.3.1 CoreRing URL 동적 설정 누락
- `/api/chat/send`에서 CoreRing 호출 URL이 `localhost:3000` 고정 → Vercel 배포 시 실패

#### 3.3.2 프론트엔드-백엔드 필드명 불일치
- 채팅: 프론트 `original` → 백엔드 `message` 기대
- CoreNull: 프론트 `action: "get-word-data"` → 백엔드 `"getWordData"` 기대

#### 3.3.3 에러 처리 불일치
- 일부 라우트는 `_error`를 사용, 일부는 `error` 필드, 일부는 `throw` → 규칙 위반

### 3.4 모듈화 실패 (패키지 발행 불가능)

**원래 목표**: 각 Core를 독립 npm 패키지로 발행
**현실**:
- 모든 코드가 하나의 Next.js 앱 내부에 위치
- `package.json` 없음, `peerDependencies` 미선언
- `supabase` 클라이언트가 하드코딩되어 있음 (주입 불가)
- 모듈 간 참조가 상대 경로로 엮여 있음 (`import from '../../sub/...'`)

## 5. 핵심 코드 문제점 요약 (수정 필요한 파일)

### 5.1 `brain-engine/layers/CoreNullLayer.js`
- **SELECT 컬럼에 존재하지 않는 `example_hue`, `example_mekong`, `cultural_note` 포함**
- **검색 조건 `standard_word` → 실제로는 `meaning_ko`로 검색해야 함**
- `saveWord`에서 불필요한 example 컬럼들 insert 시도
- `handle` 메서드는 있으나 액션 매핑이 프론트엔드와 불일치

### 5.2 `brain-engine/layers/CoreRingLayer.js`
- `new LanguageLayer()`, `new TranslationLayer()` 직접 생성 → 의존성 주입 위반
- `process()` 체이닝 → 파이프라인 무시
- Supabase 캐시 로직이 엔진에 있어야 할 것을 레이어에서 처리

### 5.3 `brain-engine/layers/CoreChatLayer.js` 및 루트 `CoreChatLayer.js`
- 두 파일 중 하나는 삭제해야 함 (정식은 `brain-engine/layers/` 내부)
- `fetch('/api/brainpool')` 호출 → 순환 참조, 제거하고 직접 번역 엔진 호출로 변경

### 5.4 `app/api/chat/send/route.ts`
- CoreRing URL을 `VERCEL_URL` 환경변수로 동적 설정해야 함 (이미 수정됨)
- DB insert 시 `original`, `translated` 컬럼 없음 → 컬럼 추가 필요
- 요청 필드 `message`와 `original` 둘 다 받도록 정규화

### 5.5 `app/api/corenull/route.ts`
- 액션명 정규화 (하이픈 → 카멜) 필요 (이미 수정됨)
- Supabase 클라이언트를 SSR로 생성해야 함 (이미 수정됨)

### 5.6 `components/WordModal.tsx` (프론트엔드)
- CoreNull 호출 시 `action: "get-word-data"` 사용 → 백엔드는 "getWordData" 기대
- 응답에서 `result.translation`을 읽어와야 함

### 5.7 `components/ChatInput` 또는 `page.tsx`
- `/api/chat/send` 호출 시 `original` 필드로 메시지 전송 → 백엔드 수정으로 해결 가능

## 6. 원하는 최종 아키텍처 (복구 목표)

### 6.1 디렉토리 구조 (모노레포)

```
packages/
├── core-ring/
│   ├── src/
│   │   ├── engine.js        # 순수 비즈니스 로직 (캐시, 감정 분석)
│   │   ├── layer.js         # Supabase 주입받는 클로저 팩토리
│   │   └── modules/         # 언어 감지, 파이프라인 등 순수 함수
│   ├── package.json
│   └── index.js             # createCoreRingLayer export
├── core-chat/
├── core-null/
├── core-child/
└── brainpool-app/           # Next.js 앱 (기존 brainpool-clean)
    └── (패키지들을 import하여 사용)
```

### 6.2 각 패키지의 표준 인터페이스

```javascript
// 패키지 index.js
export const createCoreXxxLayer = ({ supabase, deps }) => {
  // 클로저 내부에서 필요한 모듈/엔진 초기화
  const engine = createEngine(); // 순수
  const layer = async (ctx) => {
    // 1. ctx 검증
    // 2. 엔진 호출 (ctx 전달)
    // 3. DB 접근 (주입받은 supabase)
    // 4. ctx 반환
  };
  return layer;
};
```

### 6.3 API 라우트 사용 예

```javascript
// app/api/corenull/route.ts
import { createCoreNullLayer } from '@brainpool/core-null';
import { supabase } from '@/lib/supabase';

const coreNull = createCoreNullLayer({ supabase });

export async function POST(req) {
  const ctx = { payload: await req.json(), traceId: crypto.randomUUID() };
  const resultCtx = await coreNull(ctx);
  return Response.json(resultCtx._error ? { error: resultCtx._error } : { result: resultCtx.result });
}
```

## 9. 결론

**현재 프로젝트는 "모듈화된 패키지 생태계"라는 원대한 목표 아래 시작했으나, 개발 과정에서 긴급 버그 수정에 급급하여 경계가 무너지고 중복 코드가 난무하는 상태입니다.**

**하지만 핵심 비즈니스 로직은 여전히 `(ctx) => ctx` 규격을 따르고 있고, 각 Core의 클래스/객체는 분리되어 있기 때문에 위 우선순위 작업만 수행하면 원하는 모듈화를 빠르게 회복할 수 있습니다.**

**이 문서를 본 AI 또는 개발자는 위 "우선순위 작업"을 순서대로 실행하면 BRAINPOOL OS가 정상화되고 이후 패키지 발행도 가능해집니다.**
